# Read-only financial evidence reconstruction

The checker independently compares loan totals with receipt amounts, immutable allocation components, current installments, recorded amendments and early-closure source snapshots. It reports missing history separately from contradictory evidence. It does not repair records, invent historic terms or assign an assumed principal/interest split.

## Security and consistency review

1. Access: this is a local operator tool using the existing ignored configuration. It adds no API route, browser access or permission.
2. Modification: both PostgreSQL sessions explicitly use repeatable-read, read-only transactions and roll back. There are no schema, application or data writes.
3. Forgery: connection targets are restricted to the existing fixed development and staging projects. TLS verifies the Supabase CA; no caller-supplied database target is accepted.
4. Malformed evidence: monetary inputs must be finite, nonnegative, fit the existing monetary columns and have no fractions smaller than a paise. Dates, identities, versions, associations, allocation sums, paid-component bounds and amendment chains are validated. Contradictions remain failures even when other evidence is missing.
5. Direct database access: the utility verifies actual stored evidence rather than assuming materialized loan or installment totals are authoritative. This operator connection does not independently prove least-privilege runtime deployment.
6. Secrets: configuration is loaded only from existing ignored environment files. Output contains aggregate issue counts, never receipt/customer/staff rows, loan identifiers, keys, URLs or provider diagnostics. No evidence dump is created.
7. Expiry: expired database access fails without exposing diagnostics. This offline operator checker neither extends nor bypasses application authentication or MFA.
8. Concurrency: all source queries for one environment share a single repeatable-read snapshot; analysis occurs after rolling it back. Source edits after the snapshot can change a later result. No locks or mutable reconciliations are introduced.
9. Failure: setup, query, bounds and validation failures do not become successful verification. Read limits bound row counts and total JSON evidence size; network/query timeouts prevent an unlimited wait. Missing evidence and contradictions produce a non-success result.

## Evidence rules

- Cash totals include `recorded` and `verified` receipts. `reversed` and `disputed` receipts do not contribute to reconstructed current cash; immutable known evidence on these receipts is still validated. A reversal is excluded once rather than subtracted a second time.
- Regular component totals come from saved allocation rows, never from an estimated current ratio. Per-installment reconstructed principal, interest and fees are compared with stored paid components and combined amounts. When an active payment has missing evidence, known allocations still provide a lower bound and cannot exceed stored paid components. A missing historic paid split remains unknown.
- Old row-only version-one allocations can establish their receipt amount and schedule targets but cannot establish a component split. A retired reversed target without its historic schedule/amendment is missing source evidence. An active modern component allocation pointing to a retired or unavailable current target is a contradiction.
- Loan/customer/product/payment/collector associations must agree on tenant and borrower. Duplicate receipts or schedule allocations, unsupported types or component versions, invalid dates and malformed monetary values fail verification.
- Recorded restructuring versions must be consecutive. Version allocation under the loan lock supplies their causal order. PostgreSQL `now()` records transaction start, which can precede lock acquisition; equal or inverted valid timestamps do not establish a contradiction. Replaced and replacement suffixes must have unique IDs, ordered installments/dates, zero paid amounts and unwaived/unpaid status. Principal is conserved; recorded due/outstanding deltas must agree with the before/after snapshots. Replacement charges must match current rows or the exact later retirement snapshot. Borrower acceptance remains `not_recorded`; this checker cannot infer consent. Missing historic amendments are not manufactured from audit text.
- An early-closure receipt is accounted separately from regular paid installments. Its component sum and penalty must equal the receipt. Its `settledAt` must match the receipt's `collectedAt`. The captured source schedule must match the current rows' original charges and paid components; remaining rows must be waived. The saved payoff components and waiver are checked against the existing pure payoff rule using that source and timestamp. This is independent evidence reconstruction, not a second implementation or independent audit of the payoff algorithm.
- Amendment payable values require absolute agreement, not only a locally balanced difference. The checker rewinds each replacement suffix to its preserved prior suffix while retaining the untouched prefix. The resulting full schedules establish each before/after payable. Adjacent payable captures must be continuous. The latest pre-settlement payable must equal the current loan payable plus the independently verified final settlement waiver; an unavailable historic waiver is not assumed zero. These anchors reject identical offsets in before/after values even when every local delta still balances.
- Historical outstanding cannot generally be sequenced from `recordedAt`, `createdAt`, client collection dates or current reversed/disputed status. A payment on a replacement necessarily follows that replacement's creation; a whole receipt reversal necessarily precedes retirement of any of its allocated rows captured unpaid; a verified final settlement follows the recorded amendments. These causal identities can prove a receipt has no net effect at a particular capture. Where every receipt is provably absent/net zero, captured outstanding must equal the reconstructed payable. Receipts on an unchanged retained row have no durable relative operation sequence; the checker reports `amendment_payment_timeline_unproven` and an incomplete result rather than guessing their historical effect or reporting a false contradiction. Exact historical outstanding for those cases requires additional durable evidence.
- Scheduled payable, principal and unwaived outstanding are independently compared with loan totals where the source schedule can be parsed completely. A malformed row does not generate spurious aggregate differences from a deliberately incomplete projection. Old waivers without a settlement source remain missing evidence rather than an invented waiver amount.

`regularTotal` and settlement totals cover receipts whose type/evidence can be classified. A NULL allocation cannot establish whether a historical receipt was a regular payment or settlement. `componentTotalsComplete` concerns reconstructed active receipt components and must be read together with the overall state and issue lists; it is not a claim that original contracts, historical reversals or borrower acceptance are complete.

## Operator use

Build `pigmie-api`, then run `node scripts/check-financial-reconciliation.mjs`. `--development` and `--staging` restrict the fixed target; the default checks both. The script opens no writable database transaction. Its aggregate report is intentionally unsuccessful when evidence is incomplete or inconsistent. Running it against an empty staging database verifies only checker connectivity and absence of records, not posting behavior.

The pure `reconcileFinancialEvidence` utility takes one loan, all of its schedules/payments/amendments and the relevant tenant associations. Its result supplies `consistent`, `incomplete` or `inconsistent`, sorted missing/contradiction codes, and reconstructed monetary/component summaries. Tests and staged synthetic lifecycle checks may use the summaries in memory. The operator script prints only counts.

## Verification — 13–14 October 2026

Focused tests exercise consistent recorded/verified payments, reversed/disputed exclusion, balanced combined totals with a wrong component split, unknown contracts/allocations/components, old row-only evidence, mixed known/unknown lower bounds, malformed versions and duplicate allocations, fractional/nonfinite amounts, invalid dates and cross-tenant borrowers/collectors, exact settlement reconstruction, tampered settlement components/source/waiver, duplicate and reversed settlements, amendment deltas and lost/skipped identities, a two-amendment chain, recorded historical fees and missing retired reverse history.

The original 20 focused tests and the corresponding build/lint checks passed on 13 October. Independent review then found that equal offsets in amendment before/after totals could evade the local delta check. On 14 October, nine additional regressions verified the absolute and adjacent payable anchors, outstanding offsets with no historical cash, verified settlement-waiver anchoring, unknown waiver preservation, equal/inverted transaction-start timestamps, causally later payments with earlier posting timestamps, and unprovable retained-row payment/reversal ordering. All **29 focused tests passed**. The final backend build, focused ESLint and checker syntax verification passed.

The coordinating integration run on 14 October passed **478 backend tests across 40 suites**, plus live staging lifecycle/dashboard/reconstruction checks using the final built utility. Synthetic cleanup was verified. The subsequent read-only inventory matched the development counts below and confirmed staging empty and clean. These checks exercise the known synthetic cases; they do not repair the preserved historical records or prove physical cash.

Read-only development inventory found **25 loans: 13 incomplete and 12 inconsistent; none fully verified**. All 25 lack original financial contracts. Missing paid splits and missing receipt-allocation evidence each affect 14 loans. Contradictions include 11 loans with schedule payable/outstanding differences, one loan with an invalid installment, and three loans with scheduled principal differences. Categories overlap; these counts are affected loans, not individual receipts or installments. There are no orphan schedule/payment/amendment rows. Existing records remain unchanged. Staging was empty at this inventory snapshot; live known-fixture integration is recorded in the main execution report.

The tool cannot establish physical cash, historic borrower terms, undisclosed charges, borrower acceptance, payment-provider settlement, unrecorded historical event order or off-site recovery. Historic inconsistencies require source documents or a separately authorized disposition of synthetic test records. This verification adds evidence and identifies gaps; it does not declare those legacy loans repaired.
