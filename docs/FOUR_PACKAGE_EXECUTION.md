## Continuation review — financial evidence and recovery

1. Access: restructuring retains current authenticated admin/branch-manager scope checks inside the transaction. Recovery scripts connect only to validated operator development/staging targets.
2. Modification: restructuring changes only the locked scoped loan's unpaid schedule and records both schedules; historical balances are investigated read-only. No speculative historical repair is performed.
3. Forged requests: the existing validated DTO and loan/customer/staff locks enforce scope. Restore flags are allowlisted; database names are quoted and policy-role names validated.
4. Malicious clients: negative components, inconsistent loan/schedule totals and paid/waived/fee-bearing replacement rows are rejected. An unavailable profile cannot authorize offline access from cached roles.
5. Direct database access: existing browser grants remain denied. Audit snapshots do not establish an immutable amendment ledger against privileged database operators. Local restore skips owners/ACLs and cannot prove hosted least privilege.
6. Secrets: Auth/MFA database content stays inside authenticated encrypted archives and an isolated private temporary database. Recovery directories receive current-user-only Windows permissions; raw rows, provider diagnostics and credentials are suppressed.

8. Concurrency: the existing loan lock serializes application payment/restructure operations; schedule rows are locked before reading restructuring evidence. Audit failure aborts the same transaction and is verified live in staging.
9. External failure: failed profile requests do not clear device queues. Restore failure rolls back the isolated target and removes only its uniquely scoped files. Provider runtime, blob contents and independently escrowed/off-site recovery remain separate gates.

Payment retry review: only database-only payment posting opts into one retry for Prisma transaction timeout/write-conflict failures. A fresh transaction repeats authorization and looks up the same durable payment identifier; it never creates a new identifier. Emails stay after commit. Shared atomic contexts never retry an already failed parent transaction, other mutations do not opt in, validation/permission/unique errors are not retried, and existing per-attempt transaction limits remain. Retry logs contain no identifiers or raw driver messages. This is bounded recovery, not proof that timeout reliability is solved.
