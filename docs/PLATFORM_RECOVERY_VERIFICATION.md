# Platform recovery verification

## Implemented controls and current evidence

The retained local rehearsal restores application, Auth and Storage database metadata into a disposable loopback PostgreSQL cluster and compares schema/data fingerprints. Fifty tables matched in the prior staging/development exercises. Archived original migration history is included. This proves database metadata recovery only; Storage object bytes and hosted Auth/provider configuration are separate assets.

`pigmie-api/scripts/verify-offsite-backup.ts` now closes the missing remote retrieval/authentication tooling path. It reads a single explicitly selected R2 object, caps the encrypted object at 256 MiB, enforces its declared byte length, authenticates the complete AES-GCM envelope, requires a PostgreSQL custom archive signature, then invokes `pg_restore --list` without exposing its output. No plaintext is persisted or passed to the parser before authentication. The parser receives only operating-system environment variables; it does not inherit application/storage credentials. Retrieval and parsing do not apply SQL or modify any running database.

Optional `--retain-encrypted` writes only the authenticated encrypted archive and non-sensitive verification metadata in a fresh ignored `.recovery/offsite-<UUID>` directory. Unix mode 0700/0600 or current-user-only Windows permissions protect retention. It saves no encryption key. Failed retention is removed only from that uniquely created directory. Its metadata explicitly records `restoreVerified: false` and `platformRecoveryVerified: false`.

Seven regression cases verify generated object paths, exact streamed bytes, size bounds, truncation/excess bytes, wrong keys/corruption, authenticated unsupported payloads and suppressed provider diagnostics. Focused lint and tests pass. The script compiles and fails closed with fixed diagnostics when required configuration is absent. The latest local configuration presence check found all six R2/retrieval/key settings absent; remote retrieval was therefore **not performed**. GitHub/platform secret stores were not inspected or assumed absent.

## Encrypted database-and-blob bundle

`node pigmie-api/scripts/export-platform-bundle.mjs` exports fixed staging; add `--development` for the validated development project. It captures a read-only database snapshot and its public/Auth/Storage/history custom dump, releases the transaction, downloads every object listed in that snapshot, then independently re-downloads each object and checks byte hashes. A second short read-only transaction verifies unchanged Storage object identities/version/update metadata and bucket settings. Any observed change or missing object aborts export. Storage network requests do not prolong a database snapshot transaction.

This is an observed consistency check across two services, **not an atomic database/Storage snapshot**. For a guaranteed point-in-time production restore, pause uploads/deletions/metadata changes or use supported object versioning covering the database snapshot. Changes followed by an exact revert cannot be ruled out by observational checks. Application writes unrelated to captured objects after the database snapshot do not change the saved database snapshot.

The versioned binary bundle contains the PostgreSQL custom archive, every downloaded Storage byte, private bucket flags/limits/MIME policies, extension versions and hashes binding each entry. Object paths and database contents exist only inside the encrypted bundle. The manifest contains no API keys, passwords, URLs with credentials or encryption keys. Unknown versions, duplicate objects/buckets, missing bucket definitions, missing/excess bytes, hashes that disagree and unsupported database archives fail admission. Per-object content is capped at 64 MiB; the complete plaintext bundle is capped at 256 MiB with at most 10,000 objects. Those explicit bounds define this tool's supported recovery size.

The exporter persists only `platform.pgbk`, restricted ignored `.env.local` recovery keys and aggregate `verification.json` inside a unique `.recovery/platform-<UUID>` directory. A local recovery key beside an archive is not independent escrow. Use an externally supplied `BACKUP_ENCRYPTION_KEY` for established recovery workflows and independently escrow both that key and the matching PII key. No hosted runtime settings are fabricated; the manifest explicitly requires Auth settings, independent PII escrow and runtime/ACL verification.

`node pigmie-api/scripts/verify-platform-bundle.mjs platform-<UUID>` authenticates the saved envelope, validates every database/blob byte and exercises the restoration reader. It parses the real custom database archive and passes the validated blob bytes through read-only destination adapters. It performs no hosted restore or remote writes. `restorePlatformBundle` exposes verified database and object callbacks for a separately controlled destination; all entries are validated before any destination callback runs. Destination adapters must independently enforce destination identity, private bucket settings, database/provider compatibility, rollback/retry handling and post-restore hash/ACL verification. The callback interface is not a claim that those hosted checks ran.

Nine bundle regression cases cover exact content, empty Storage, database/blob corruption, missing/excess bytes, duplicate/missing buckets/objects, unsafe paths, unsupported formats/lengths and validation before restoration callbacks. Existing archive authentication tests separately cover wrong keys/header/ciphertext/tag tampering. Seventeen combined retrieval/bundle tests pass. A complete hosted exercise is still required to prove Auth sign-in/MFA/revocation and Storage private access after restore.

Read-only staging and development exports passed and their persisted encrypted bundles authenticated. Both current sources had two buckets and **zero Storage objects**, so the real custom database archives and empty inventories were exercised; no existing blob bytes were available for a live blob round trip. Both saved bundles passed the database parser/restoration-reader checks. Sixteen focused recovery tests pass, with focused lint and script syntax checks. The source database connections were closed and no hosted mutations occurred in those exports.

## Running the read-only remote check

Run from `pigmie-api` with these settings supplied through an ignored environment file or platform secret store:

- `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`: a read-only object-storage credential is sufficient for this verifier; use a separate writer credential for backup production.
- `BACKUP_ENCRYPTION_KEY`: the independent 32-byte hexadecimal recovery key matching the selected backup. Obtain it from approved escrow, not the same artifact folder.
- `BACKUP_OBJECT_KEY`: the exact `backups/backup-YYYY-MM-DDTHH-mm-ss-SSSZ.pgbk` object generated by the backup workflow.
- `PG_RESTORE_PATH`: optional local PostgreSQL restore executable path.

Execute `npx ts-node scripts/verify-offsite-backup.ts`; add `--retain-encrypted` only when encrypted local retention is needed. Do not put any secret values into command arguments, checked-in examples or chat. Default output contains status flags only. Archives larger than the cap fail; production-scale recovery needs a separately reviewed authenticated spool implementation rather than raising the cap without a memory assessment.

Provider migrations/roles/extensions and target version must be checked using an isolated target first. Re-create service/API keys at the destination rather than copying exposed tokens. Preserve database identity/PII encryption keys through controlled escrow when ciphertext requires them; key rotation alone cannot decrypt old ciphertext.

The fixture/restore threat review: (1) only the authorized operator's staging service key can create the synthetic object; (2) mutations are confined to one unique journaled identity, with no bucket policy changes; (3) fixed validated project and encoded paths prevent arbitrary-host/path requests; (4) the authenticated reader validates all entries before restore, while the isolated destination identity is fixed; (5) the source snapshot is read-only and destination roles are local non-login placeholders; (6) secrets are limited to ignored environment files and process memory with suppressed diagnostics; (7) expired credentials abort without anonymous fallback; (8) unique fixture/cluster IDs and double-read source consistency checks prevent collisions and fail observed concurrent changes; (9) bounded network/process operations, exact cleanup and persistent non-secret journal support safe failure recovery.

## Threat review

1. Access: only an authorized operator with explicit read-only object credentials and the recovery key can retrieve/authenticate an archive.
2. Modification: the verifier modifies no remote object/database; optional writes are confined to its unique ignored restricted local directory.
3. Forgery: a fixed HTTPS R2 account endpoint and generated-object path syntax reject arbitrary URLs and traversal input.
4. Malicious object: length bounds, GCM authentication and archive parser rejection fail closed before restoration; authenticated SQL is never executed by this check.
5. Direct database access: this tool has no database connection and does not claim ACL/RLS restore proof.
6. Secrets: credentials remain in environment/secret stores, keys are never retained by this tool, diagnostics/TOC and plaintext are suppressed; plaintext memory is cleared after use.
7. Expiry: expired storage credentials fail closed without fallback credentials or anonymous object access.
8. Concurrency: unique retention directories and exclusive writes prevent collisions; a single-object GET plus authenticated envelope rejects mixed/truncated data.
9. External failure: bounded download/parser timeouts fail safely, client resources close, unsuccessful retention is removed, and no production restore occurs.
